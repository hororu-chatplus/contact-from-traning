# 要件定義書 - お問い合わせフォーム

## 1. 概要

ChatPlusのWebサイトに、お問い合わせフォームを設置する。
現状はお問い合わせをメールで受信して運用しているが、他のメールに埋もれて管理が難しいため、お問い合わせ内容をシステム上で一覧管理できるようにし、対応状況の管理を改善する。

## 2. 目的

- ユーザーが会社名・氏名・メールアドレス等を入力し、お問い合わせを送信できるようにする
- 入力内容に不備がある場合は、送信前にエラーを表示し、ユーザーに修正を促す
- 送信が完了したことをユーザーに分かりやすく伝える
- お問い合わせ内容をデータベースに保存し、管理者が一覧で確認・対応管理できるようにする
- 管理者機能はログインしたユーザーのみ利用できるようにする

## 3. 利用者

- Webサイトを訪れる一般ユーザー（会員登録などは不要、誰でも利用可能）
- 管理者（ログインして、お問い合わせの一覧・詳細確認・返信・編集・削除を行う）。初期の利用者としてホロル様・八島様・赤松様の3名を想定

## 4. 機能要件

### 4.1 お問い合わせフォーム

| No | 機能 | 内容 |
|----|------|------|
| F-01 | 入力フォーム表示 | 会社名・部署名・役職・氏名・メールアドレス・電話番号・ご担当・ChatPlusについて・サービス項目・問い合わせ内容の入力欄を表示する |
| F-02 | 入力チェック（バリデーション） | 必須項目の未入力、メールアドレスの形式不正、フリーメールアドレスを検知しエラー表示する。バリデーションはクライアント側・サーバー側の両方で行う |
| F-03 | 確認画面表示 | 入力チェックを通過したら、入力内容を確認する画面を表示する |
| F-04 | 送信・完了画面表示 | 確認画面で送信を実行したら、DBへの保存・メール送信を行い、完了画面を表示する |
| F-05 | エラー表示 | エラー項目には赤枠とエラーメッセージを表示する |
| F-06 | データベース保存 | お問い合わせ内容をデータベースに保存する |
| F-07 | 自動返信メール送信 | 入力されたメールアドレス宛に、お問い合わせを受け付けた旨のメールを送信する |
| F-08 | 管理者通知メール送信 | support@chatplus.jp 宛に、お問い合わせがあった旨のメールを送信する |
| F-09 | reCAPTCHA | スパム対策としてreCAPTCHAを設置する（任意項目）。バージョン（v2/v3）・導入方式に特に指定はないため、実装者の裁量で選定する。本番運用開始時には、確定したドメイン（chatplus.jp）でGoogle reCAPTCHA管理コンソールから取得した本番用キーに差し替える（2026-08-13のヒアリングで確定） |

### 4.2 ログイン

| No | 機能 | 内容 |
|----|------|------|
| F-10 | ログイン機能 | 管理者アカウントのログインID・パスワードでログインできるようにする。ログインIDの代わりに、登録済みのメールアドレスでもログインできる（2026-08-14のヒアリングで追加。ログインIDを忘れた場合の救済手段）。メールアドレスは管理者アカウント間で重複登録できない |
| F-11 | ログイン試行回数制限 | ログイン失敗が一定回数（例: 5回）連続した場合、一定時間アカウントをロックし、ブルートフォース攻撃を防止する |
| F-12 | 管理者アカウント管理 | 管理者アカウントの一覧表示・新規登録・有効／無効切替を行う機能を提供する（S-08 管理者アカウント管理画面） |
| F-13 | アクセス制御 | 未ログイン状態で管理者向け機能（一覧・詳細・削除・編集・アカウント管理）にアクセスした場合、ログイン画面に遷移させる。なお、利用者向け画面（S-01〜S-03）にはログイン画面への導線（リンク等）を意図的に設置しない。管理者にはログイン画面のURLを個別に共有する運用とする（2026-08-20の確認事項。詳細は画面設計書1章参照） |
| F-23 | 不正ログイン警告通知 | ログイン失敗によりアカウントがロックされた場合（F-11）、対象の管理者本人のメールアドレス宛に警告通知メールを送信する。ロックされるたびの通知であり、失敗のたびには送信しない。本機能のため、管理者アカウントにメールアドレス項目を追加する必要がある（設計書側で反映） |
| F-24 | パスワード再設定 | 管理者がパスワードを忘れた場合に、登録済みのメールアドレスを用いて自分でパスワードを再設定できる機能を提供する（2026-08-13のヒアリングで追加。開発者によるCLIでの手動対応のみでは運用上望ましくないとの結論による。9章の対象外からも除外） |

### 4.3 お問い合わせ一覧・詳細

| No | 機能 | 内容 |
|----|------|------|
| F-14 | 一覧表示 | 会社名・氏名・メールアドレス・サービス項目・ChatPlusについて・問い合わせ内容・登録日時・対応状況（ステータス）を一覧表示する。ご担当は一覧には表示せず、詳細画面（F-15）でのみ確認する（2026-08-13のヒアリングで確定）。対応状況の列は一覧の左端に配置する。件数増加に備え、対応状況・サービス項目による絞り込みと、キーワードによる検索を行えるようにする。絞り込み条件は「すべて」等の表記だけでは何を絞り込んでいるか分かりにくいため、対応状況の絞り込みであることが分かるように表示する。サービス項目は種類ごとに色分け表示し、視認性を高める。1ページあたりの表示件数は20件・50件・100件から選択できるようにし、デフォルトは20件とする。会社名・氏名・メールアドレス列は表示文字数を短縮し、ChatPlusについて列まで折り返しなく見えるよう一覧テーブル全体の横幅を広げる。ページ切り替え（ページネーション）は一覧テーブルの上下両方に表示する（いずれも2026-08-14のヒアリングで追加。会社名列の短縮は同日追って追加） |
| F-15 | 詳細表示 | 一覧から選択したお問い合わせの詳細（全入力項目）を表示する。ステータス変更・メモ編集・返信への導線をこの画面に設ける |
| F-16 | ステータス管理 | お問い合わせごとに「未対応」「対応済」のステータスを管理する。メール返信（F-17）を送信すると、ステータスは自動的に「対応済」に変更される |
| F-17 | メール返信 | 詳細画面からお問い合わせ元へメール返信ができる。返信を送信すると、ステータスは自動的に「対応済」に変更される（F-16）。返信の送信履歴は、宛先・件名・送信日時に加え、本文も記録する。送信元アドレスは、自動返信（F-07）と同じno-reply@chatplus.jpではなく、返信可能なアドレス（例: support@chatplus.jp）とする（2026-08-13のヒアリングで確定）。管理者が入力するのは件名と本文の要点のみとし、送信メールには宛名（お問い合わせ元の氏名）・元のお問い合わせ内容の引用・署名を自動的に付加する。件名には他の自動送信メールと同じ「【ChatPlus】」の接頭辞を自動的に付ける（2026-08-13の実装レビューで追加） |

| No | 機能 | 内容 |
|----|------|------|
| F-21 | 個人情報の開示・訂正・削除請求への対応 | 本人（お問い合わせを行った利用者）から開示・訂正・利用停止の請求があった場合は、管理画面の詳細表示・メモ編集・削除機能（F-15・F-18・F-20）を用いて個別に対応する。保存期間による自動削除は行わない（1日あたりの件数が少なく、運用上不要と判断） |

## 7. 非機能要件

- スマートフォン・PCの両方で見やすいレイアウトにする（レスポンシブ対応必須）
- サーバーサイド：PHP
- データベース：MySQL
- 通信はHTTPS（常時SSL/TLS化）を必須とする
- 想定件数：お問い合わせは1日あたり最大50件程度を想定する
- デザインは、ChatPlus本体の既存のお問い合わせ関連ページ（https://chatplus.jp/cp_contact/ ）のトーン・スタイルに合わせる（2026-08-13のヒアリングで確定）
- 本番環境のドメインはchatplus.jpとする。管理画面のURL構成には特に指定はない（実装者の裁量とする）（2026-08-13のヒアリングで確定）
- 本番ホスティング環境はWordPressが稼働する環境（共用ホスティング相当）であることを確認した（2026-08-14のヒアリングで確定）。これに伴い、共用ホスティング環境で起こり得るログイン失敗回数カウントの競合対策、およびallow_url_fopen無効化を想定したreCAPTCHA検証処理への変更を行う
- 本番環境では、自動返信（F-07）・管理者通知（F-08）・個別返信（F-17）のメールは、外部のメール配信サービス（例: Gmail等のSMTP）を利用して実際に送信されるようにする。開発・研修環境ではモック送信（ログ記録のみ）のままで構わない（2026-08-13のヒアリングで確定）

## 8. セキュリティ要件

本システムはIPA「安全なウェブサイトの作り方」の指針に基づき、以下のセキュリティ対策を実装する。

### 8.1 SQLインジェクション対策

- SQL文の組み立ては、原則としてプレースホルダ（プリペアドステートメント）を用いて実装する。
- 文字列連結によりSQL文を構成する場合は、アプリケーションの変数をSQL文のリテラルとして正しく扱われるようエスケープ処理を行う。
- Webアプリケーションに渡されるパラメータに、SQL文（の一部）を直接指定できないようにする。
- データベースエラー発生時、SQL文やテーブル構造等が含まれるエラーメッセージをそのままブラウザに表示しない。

### 8.2 パス名パラメータの未チェック・ディレクトリトラバーサル対策

- 外部パラメータでサーバー内のファイルパスを直接指定させる実装を避ける。
- Webサーバ内のファイルへのアクセス権限を必要最小限に設定する。
- 外部からファイル名を受け取る場合は、許可する文字種・拡張子のチェックを行う。

### 8.3 セッション管理の不備対策

- セッションIDは、フレームワーク標準のセッション管理機構を用い、推測が困難な値を使用する。セッションIDを固定値にしない。
- セッションIDをURLパラメータに格納しない（Cookieのみで管理する）。
- HTTPS通信を前提とし、CookieにはSecure属性を付与する。
- ログイン成功後は、新しくセッションを開始する（ログイン前後でセッションIDを再発行する）。
- セッションCookieには適切な有効期限を設定する。

### 8.4 クロスサイト・スクリプティング（XSS）対策

- 画面に出力する全ての要素（問い合わせ内容、会社名、氏名等のユーザー入力値を含む）にエスケープ処理を行う。
- 入力値を用いて`<script>...</script>`要素の内容を動的に生成しない。
- スタイルシートを任意の外部サイトから取り込めるようにしない。
- 入力値については文字種・文字数などの内容チェックを行う。
- HTTPレスポンスヘッダのContent-Typeフィールドに文字コード（charset=UTF-8）を明示する。

### 8.5 CSRF（クロスサイト・リクエスト・フォージェリ）対策

- お問い合わせ送信・ログイン・編集・削除等、処理を実行するページはPOSTメソッドでアクセスする。
- 前のページ（フォーム）に秘密情報（CSRFトークン）を埋め込んだhiddenパラメータを自動生成し、実行ページではその値が正しい場合のみ処理を実行する。

### 8.6 メールヘッダ・インジェクション対策

- メールヘッダ（From、Subject等）は固定値とし、外部からの入力値はすべてメール本文に出力する。
- HTMLフォームの入力値で宛先（To）を指定できないようにする。

### 8.7 クリックジャッキング対策

- HTTPレスポンスヘッダにX-Frame-Optionsフィールドを出力し、他ドメインのサイトからframe要素・iframe要素で読み込まれることを制限する。特にログイン画面・お問い合わせ一覧画面等の管理者向け画面に適用する。

### 8.8 アクセス制御・認可制御の欠落対策

- 管理者向け機能（一覧・詳細・削除・編集）には、ID・パスワードによる認証機能を設ける（4.2 ログイン機能）。
- 認証機能に加えて認可制御を実装し、ログイン中の利用者が他の利用者になりすましてアクセスできないようにする。
- 削除・編集操作は操作ログとして記録する（4.4 F-19）。

### 8.9 認証情報の管理

- 管理者パスワードは、ソルト付きハッシュ関数（bcrypt等）を用いて保存し、平文やリバーシブルな暗号化方式では保存しない。
- 管理者パスワードは8文字以上72文字以内とし、半角英数字に加えて記号を1文字以上含めることを必須とする（上限はbcryptハッシュ関数が72バイトを超える部分を無視する仕様のため、実装者の判断で追加）。
- ログイン失敗が一定回数（5回）連続した場合はアカウントを一時ロックする（30分。4.2 F-11）。
- アカウントがロックされた場合、対象の管理者本人のメールアドレス宛に警告通知メールを送信する（4.2 F-23）。

### 8.10 個人情報の保護

本システムは会社名・氏名・電話番号・メールアドレスといった個人情報を取り扱うため、8.1〜8.9の技術的対策に加えて、以下の対策を行う。

- 入力画面にプライバシーポリシーへのリンク（https://chatplus.jp/policy/privacy/）を表示し、送信前に同意のチェックボックスへのチェックを必須とする（4.6 F-22）。
- 取得した個人情報は、お問い合わせへの対応目的以外に利用しない。第三者への提供は行わない。
- 個人情報を閲覧・変更できるのは、ログインした管理者アカウントに限定する（8.8のアクセス制御を適用する）。
- 本人（お問い合わせを行った利用者）から開示・訂正・削除の請求があった場合は、既存の管理画面（詳細表示・メモ編集・削除機能）を用いて個別に対応する。専用の請求受付画面は設けない。保存期間による自動削除は行わない（4.6 F-21）。
