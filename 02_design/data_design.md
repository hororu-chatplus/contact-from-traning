## 3. チェックタイミング

- クライアント側: 入力欄からフォーカスが外れた時（blur時）に該当項目のみ再チェックし、「確認する」押下時に全項目をチェックする

## 4. データベース設計

### 4.0 共通事項

- 文字コード・照合順序: 全テーブル `utf8mb4` / `utf8mb4_unicode_ci` を使用する（絵文字を含む日本語入力に対応するため）
- created_at は登録（INSERT）時に `DEFAULT CURRENT_TIMESTAMP` で自動設定する
- updated_at は更新のたびに `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` により自動更新する

### 4.1 inquiries（お問い合わせ）テーブル

| カラム名 | 型 | 制約 | 内容 |
|----------|-----|------|------|
| id | BIGINT | PK, AUTO_INCREMENT | お問い合わせID |
| company_name | VARCHAR(50) | NOT NULL | 会社名 |
| department | VARCHAR(50) | NULL | 部署名 |
| position | VARCHAR(50) | NULL | 役職 |
| name | VARCHAR(50) | NOT NULL | 氏名 |
| email | VARCHAR(256) | NOT NULL | メールアドレス |
| phone | VARCHAR(15) | NOT NULL | 電話番号（ヒアリングにより必須項目に変更） |
| contact_role | ENUM('経営者','情報システム関連部門（ツール選定等のご担当）','カスタマーサポート部門（コンタクトセンター）','問い合わせ対応部門','販促・営業・マーケティング部門','お客様への提案（代理店）','その他') | NOT NULL | ご担当 |
| chatplus_status | ENUM('利用中','検討中（3か月以内）','検討中（1年以内）','検討中','他社サービス利用中','詳しく話が聞きたい','その他') | NOT NULL | ChatPlusについて |
| service_type | ENUM('ChatPlus','FAQPlus','AI AgentPlus') | NOT NULL | サービス項目（ヒアリングにより任意→必須に変更） |
| content | VARCHAR(1000) | NOT NULL | 問い合わせ内容（列定義自体で文字数上限を担保） |
| memo | VARCHAR(1000) | NULL | 管理者メモ（社内向け、要件 F-20） |
| status | ENUM('未対応','対応済') | NOT NULL, DEFAULT '未対応' | 対応状況（要件 F-16） |
| created_at | DATETIME | NOT NULL | 登録日時 |
| updated_at | DATETIME | NOT NULL | 更新日時 |

- SQL発行はプレースホルダ（プリペアドステートメント）を使用する（要件 8.1）
- contact_role・chatplus_status・service_type・statusはENUM型とし、アプリ層の不具合や直接INSERTによって選択肢外の値が入らないようDBレベルでも制約する
- 一覧・詳細画面への出力時は、company_name / department / position / name / content / memo 等すべての値をエスケープ処理した上で表示する（要件 8.4）
- プライバシーポリシーへの同意（要件 F-22）は送信条件であり、保存されるお問い合わせは全件同意済みであることが送信処理側で保証されるため、同意記録用のカラムは設けない（同意日時はcreated_atと同一とみなす）。将来ポリシー改定に伴う再同意の要件が生じた場合は、同意バージョンを記録するカラムの追加を検討する
- 個人情報の保存期間（要件 8.10・4.6 F-21）については、ヒアリングの結果、件数が少ない（1日最大50件程度）ため自動削除は行わない方針に確定した。開示・訂正・削除の請求があった場合は、既存の削除機能（F-18）・メモ編集機能（F-20）を用いて管理者が個別に対応する。自動削除用のカラムやバッチ処理は設けない

### 4.2 admin_users（管理者アカウント）テーブル

| カラム名 | 型 | 制約 | 内容 |
|----------|-----|------|------|
| id | BIGINT | PK, AUTO_INCREMENT | 管理者ID |
| login_id | VARCHAR(50) | NOT NULL, UNIQUE | ログインID |
| email | VARCHAR(256) | NOT NULL, UNIQUE | 通知先メールアドレス（要件 F-23）。ログインIDの代わりにログイン識別子としても使用する（要件 F-10、2026-08-14のヒアリングで追加）。ログインでの一意性を保証するため、login_idと同様にUNIQUE制約を付与する |
| password_hash | VARCHAR(255) | NOT NULL | パスワード（bcrypt等によるソルト付きハッシュ、要件 8.9） |
| login_fail_count | INT | NOT NULL, DEFAULT 0 | ログイン連続失敗回数（要件 F-11） |
| locked_until | DATETIME | NULL | アカウントロック解除日時（NULLはロックなし） |
| is_active | TINYINT(1) | NOT NULL, DEFAULT 1 | 有効／無効フラグ。無効化されたアカウントはログイン不可 |
| password_reset_token | VARCHAR(64) | NULL | パスワード再設定用トークン（要件 F-24。未依頼時はNULL） |
| password_reset_expires_at | DATETIME | NULL | パスワード再設定用トークンの有効期限（要件 F-24） |
| created_at | DATETIME | NOT NULL | 作成日時 |
| updated_at | DATETIME | NOT NULL | 更新日時 |

- ログイン失敗のたびに login_fail_count を加算し、一定回数（5回。要件 8.9で確定）到達で locked_until に現在時刻+一定時間（30分。要件 8.9で確定）を設定する
- ログイン成功時は login_fail_count を0にリセットする
- locked_until を新たに設定した（＝ロックが発生した）タイミングでのみ、そのアカウントの email 宛にロック警告通知メールを送信する（要件 F-23）。詳細な送信条件は5.1参照
- 管理者アカウントを使わなくする場合は is_active を0にする運用とし、物理削除は行わない（operation_logsとの参照整合性・監査ログの保全のため）
- is_active=0への変更は、ログイン画面での新規ログイン拒否だけでなく、既にログイン中のセッションにも次回アクセス時点で反映する（管理者向けページ共通の認証チェックでis_activeを都度確認する。2026-08-13の実装レビューで追加）
- パスワード再設定（要件 F-24）の依頼時、暗号学的に安全な乱数から生成したトークン（32バイト・16進数64桁）を password_reset_token に、現在時刻+30分（ログインロック時間8.9と同じ長さとし実装者の裁量で統一）を password_reset_expires_at に設定する。再設定完了時、または新たに再設定を依頼した時点で、古いトークンは上書き・無効化される（使い捨てトークン）

### 4.3 operation_logs（操作ログ）テーブル

| カラム名 | 型 | 制約 | 内容 |
|----------|-----|------|------|
| id | BIGINT | PK, AUTO_INCREMENT | ログID |
| admin_id | BIGINT | NOT NULL, FK → admin_users.id (ON DELETE RESTRICT) | 実行した管理者 |
| inquiry_id | BIGINT | NULL, FK → inquiries.id (ON DELETE SET NULL) | 対象のお問い合わせ（削除後はNULLになる） |
| action_type | VARCHAR(10) | NOT NULL | edit（メモ・ステータス編集）/ delete（削除）/ reply（返信送信） |
| target_summary | VARCHAR(500) | NOT NULL | 対象のスナップショット（action_typeにより書式が異なる。下記参照） |
| reply_body | VARCHAR(4000) | NULL | 返信メール本文（action_type='reply'の場合のみ格納。要件 F-17。ヒアリングにより本文も保存する方針に確定） |
| created_at | DATETIME | NOT NULL | 実行日時 |

- 削除（要件 F-18）は物理削除とするため、inquiry_id は削除後に参照できなくなる。そのため target_summary に削除実行時点の会社名・氏名を保存し、削除後も「誰が・いつ・何を」削除したか追跡できるようにする
- admin_id はON DELETE RESTRICTとし、操作ログが残る管理者アカウントを誤って物理削除できないようにする（4.2の通り、通常運用ではis_activeによる無効化を用いる）
- action_type='reply'の場合、target_summaryに宛先・件名の要約を、reply_bodyに送信した本文全体（最大4000文字）を格納する。edit・deleteの場合はreply_bodyはNULLのまま使用しない
- target_summaryのフォーマット:
  - edit / delete: `会社名: {company_name} / 氏名: {name}`
  - reply: `宛先: {email} / 件名: {subject}`

### 4.4 インデックス設計

| テーブル | インデックス | 目的 |
|----------|--------------|------|
| inquiries | INDEX(status) | 一覧画面（S-05）のステータス絞り込み |
| inquiries | INDEX(created_at) | 登録日時順の並び替え・ページネーション |
| operation_logs | INDEX(inquiry_id) | 対象お問い合わせに紐づく操作履歴の参照 |
| operation_logs | INDEX(admin_id) | 管理者ごとの操作履歴の参照 |
| operation_logs | INDEX(created_at) | 期間指定でのログ参照 |
| admin_users | UNIQUE INDEX(password_reset_token) | パスワード再設定画面（S-10）でのトークン照合（要件 F-24） |
| admin_users | UNIQUE INDEX(email) | ログイン画面（S-04）でのメールアドレスによる照合（要件 F-10、2026-08-14のヒアリングで追加） |

一覧画面のキーワード検索（会社名・氏名・メールアドレス）は当面 `LIKE` 検索で対応し、専用インデックスは設けない。データ量が増加した場合はFULLTEXTインデックスの追加を検討する。

一覧画面の1ページあたり表示件数（要件 F-14）は20／50／100件から選択できるようにし、デフォルトは20件とする。選択値はクエリパラメータで保持し、DB設計上の変更は不要（LIMIT句の値のみ可変にする）。

## 5. 管理者ログイン 入力項目・バリデーション

| 項目ID | 項目名 | input要素 | 必須 | ルール | エラーメッセージ |
|--------|--------|-----------|------|--------|-------------------|
| identifier | ログインID または メールアドレス | text | ○ | 空欄不可 | ログインIDを入力してください |
| password | パスワード | password | ○ | 空欄不可 | パスワードを入力してください |

- 認証時は入力値をlogin_idとemailの両方に対して照合し、いずれかに一致すればそのアカウントとして扱う（要件 F-10、2026-08-14のヒアリングで追加。ログインIDを忘れた場合の救済手段）。emailはUNIQUE制約により一意なので、一致するアカウントは常に高々1件に定まる
- 認証失敗時は「IDまたはパスワードが正しくありません」の共通メッセージのみを表示し、ログインID・メールアドレス・パスワードのどれが誤りかを特定させない
- アカウントロック中は「試行回数の上限に達しました。しばらく経ってから再度お試しください」と表示する
- is_active が0（無効）のアカウントは、パスワードが正しい場合でもログインを拒否する

### 5.1 ログインロック時の警告通知（要件 F-23）

- login_fail_count が上限（5回）に達し、locked_until を新たに設定する更新を行った回のみ、そのアカウントの admin_users.email 宛に警告通知メールを送信する
- 既に locked_until が未来に設定されている状態（ロック中）でさらにログインが試行されても、通知メールは再送信しない（ロックのたびに1回だけ送信するという要件 F-23の仕様を満たすため。判定は「今回の更新でlocked_untilをNULL/期限切れの状態から新たに設定したか」で行う）
- ログイン成功によりlogin_fail_countが0にリセットされた場合、ロック状態も解消される
- 通知メールの件名・本文の固定文言は2026-08-07に確定した（`03_implementation/login.php`参照）

## 6. 管理者操作 入力項目・バリデーション

### 6.1 ステータス変更・メモ編集（S-06 詳細画面）

| 項目ID | 項目名 | input要素 | 必須 | ルール | エラーメッセージ |
|--------|--------|-----------|------|--------|-------------------|
| status | ステータス | select | ○ | 選択肢（未対応／対応済）以外の値を許可しない | 不正なステータスが指定されています |
| memo | メモ | textarea | - | 1000文字以内 | メモは1000文字以内で入力してください |

ステータス変更・メモ編集はいずれも実行者・実行日時をoperation_logsにaction_type='edit'として記録する（要件 F-19）。ステータスは、この画面からの手動変更に加えて、返信メール送信（6.2）によっても自動的に「対応済」へ更新される（要件 F-16）。

### 6.2 返信メール（S-07 返信画面）

| 項目ID | 項目名 | input要素 | 必須 | ルール | エラーメッセージ |
|--------|--------|-----------|------|--------|-------------------|
| reply_subject | 件名 | text | ○ | 空欄不可、200文字以内 | 件名を入力してください／件名は200文字以内で入力してください |
| reply_body | 本文 | textarea | ○ | 空欄不可、4000文字以内 | 本文を入力してください／本文は4000文字以内で入力してください |

宛先はお問い合わせのemailを使用し、フォーム経由での変更は受け付けない（要件 8.6 メールヘッダ・インジェクション対策）。返信メールを送信すると、当該お問い合わせのstatusを自動的に「対応済」に更新する（要件 F-16・F-17。ヒアリングにより、以前の「返信とステータス変更は独立」という仕様から変更）。送信の実行者・宛先・件名・本文・実行日時はoperation_logsにaction_type='reply'として記録する（本文はreply_bodyカラムに格納。ヒアリングにより本文も保存する方針に確定。ここに格納するのは管理者が入力した本文のみで、下記のテンプレートで付加した宛名・引用・署名は含まない）。

件名には他の自動送信メール（自動返信・管理者通知・ロック警告・パスワード再設定）と同じ「【ChatPlus】」の接頭辞を、管理者が入力した件名の前に自動的に付ける（ブランド表記の統一。2026-08-13の実装レビューで追加）。operation_logsのtarget_summaryには、この接頭辞を付けた実際の送信件名を記録する。

管理者が入力した本文をそのままメール送信するのではなく、宛名・元のお問い合わせ内容の引用・署名を付けた以下の構成で送信する（2026-08-13の実装レビューで追加）。

```
{氏名} 様

お問い合わせいただき、誠にありがとうございます。
ChatPlus サポート窓口でございます。

{管理者が入力した本文}

-----------------------------------
【お問い合わせ内容】
{元のお問い合わせ内容}
-----------------------------------

ご不明な点がございましたら、本メールに直接ご返信いただくか、お気軽にお問い合わせください。

ChatPlus サポート窓口
support@chatplus.jp
```

返信メールのFromアドレスは、自動返信・管理者通知（no-reply@chatplus.jp）とは別に、返信可能なアドレス（例: support@chatplus.jp）を使用する（要件 F-17、2026-08-13のヒアリングで確定）。送信元を用途ごとに使い分けられるよう、メール送信処理は宛先種別（自動返信・管理者通知・個別返信）に応じたFromアドレスを選択できる構成とする。

### 6.3 管理者アカウント新規登録（S-08 管理者アカウント管理画面）

| 項目ID | 項目名 | input要素 | 必須 | ルール | エラーメッセージ |
|--------|--------|-----------|------|--------|-------------------|
| login_id | ログインID | text | ○ | 空欄不可、3〜50文字、既存login_idと重複不可 | ログインIDを入力してください／このログインIDは既に使用されています |
| email | メールアドレス | email | ○ | 空欄不可、メール形式、256文字以内、既存emailと重複不可（要件 F-10でログイン識別子を兼ねるため、2026-08-14のヒアリングで追加） | メールアドレスを入力してください／正しい形式のメールアドレスを入力してください／このメールアドレスは既に使用されています |
| password | パスワード | password | ○ | 空欄不可、8文字以上72文字以内、半角英数字に加えて記号を1文字以上含む（要件 8.9で確定） | パスワードを入力してください／パスワードは8文字以上72文字以内で、半角英数字に加えて記号を1文字以上含めてください |
| password_confirm | パスワード（確認用） | password | ○ | passwordと一致すること | パスワードが一致しません |

登録成功時、passwordはソルト付きハッシュ関数（bcrypt等）でハッシュ化し`admin_users.password_hash`に保存する（要件 8.9）。登録するemailは、そのアカウントがロックされた際の警告通知先として使用する（要件 F-23）。有効／無効切替の操作は、対象が自分自身のアカウントである場合は拒否する（管理者が自分を無効化して誰もログインできなくなる事態を防ぐため）。

### 6.4 パスワード再設定（S-09 依頼画面／S-10 新しいパスワード設定画面）要件 F-24

**S-09（依頼）**

| 項目ID | 項目名 | input要素 | 必須 | ルール | エラーメッセージ |
|--------|--------|-----------|------|--------|-------------------|
| identifier | ログインID または メールアドレス | text | ○ | 空欄不可 | ログインIDまたはメールアドレスを入力してください |

- ログインID・メールアドレスのどちらでも依頼できる（要件 F-10、2026-08-14のヒアリングで追加。S-04ログイン画面と同様、ログインIDを忘れた場合の救済手段）。入力値をlogin_id・emailの両方に対して照合する
- 該当するアカウントがadmin_usersに存在するかどうかに関わらず、常に同一の完了メッセージを表示する（アカウントの有無を外部から推測できないようにするため。S-04ログイン画面と同じ考え方）
- 該当するアカウントが存在する場合のみ、4.2の通りトークンを発行し、そのアカウントのemail宛にパスワード再設定用リンク（例: `/reset_password.php?token={トークン}`）を記載したメールを送信する。文面は実装時に確定する（F-23の通知メールと同様のパターン）
- reCAPTCHA等のスパム対策は本画面では必須としない（要件未指定、実装者の裁量とする）

**S-10（新しいパスワード設定、URLの`token`クエリパラメータで対象アカウントを特定）**

| 項目ID | 項目名 | input要素 | 必須 | ルール | エラーメッセージ |
|--------|--------|-----------|------|--------|-------------------|
| password | 新しいパスワード | password | ○ | 空欄不可、8文字以上72文字以内、半角英数字に加えて記号を1文字以上含む（要件 8.9と同一ポリシー） | パスワードを入力してください／パスワードは8文字以上72文字以内で、半角英数字に加えて記号を1文字以上含めてください |
| password_confirm | 新しいパスワード（確認用） | password | ○ | passwordと一致すること | パスワードが一致しません |

- 画面表示前に、tokenがpassword_reset_tokenと一致し、かつpassword_reset_expires_atが現在時刻より未来であるレコードを検索する。該当がなければフォームを表示せず「このリンクは無効か、有効期限が切れています」と表示する
- 更新成功時、password_hashを新しい値に更新し、password_reset_token・password_reset_expires_atをNULLに戻す（トークンは使い捨て）。あわせてlogin_fail_countを0に、locked_untilをNULLにリセットする（アカウントロック中でも再設定後は速やかにログインできるようにするため）
- 本画面の処理はoperation_logsへの記録対象外とする（4.3の通り、operation_logsはお問い合わせに対する操作を対象とするため）

## 7. 送信後の処理（本番仕様）

- クライアント側・サーバー側の両方でバリデーションを通過した内容のみをDBに保存する
- reCAPTCHA検証に成功した場合のみ送信処理を実行する
- 保存後、入力されたメールアドレス宛に自動返信メール、support@chatplus.jp 宛に管理者通知メールをそれぞれ送信する（要件 F-07・F-08）
- メール送信時、Fromなどのヘッダは固定値とし、外部入力はメール本文にのみ出力する（要件 8.6）
